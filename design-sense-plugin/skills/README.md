# Design Sense

사용자의 작업을 중심으로 인터페이스를 **설계·구현·리뷰·재현**하는 AI 에이전트 스킬입니다. 요구사항을 화면과 동작의 결정으로 연결하고, 실제 콘텐츠와 실행 중인 인터페이스를 통해 결과를 검증합니다.

스킬 이름은 `design-sense`이며, 실행 지침의 기준 문서는 [SKILL.md](SKILL.md)입니다.

## 사용 가이드

사용하는 코딩용 에이전트 도구를 -a으로 명시

```
$ npx skills add https://github.com/pjt3591oo/claude-code-advanced-guide/tree/main/design-sense-plugin -a claude-code -a opencode -a codex
```

## 언제 사용하나요?

- 새로운 제품의 UI와 대표 사용자 흐름을 설계하고 구현할 때
- 기존 앱의 화면이나 상호작용을 크게 개선할 때
- 토큰, 컴포넌트, 반복 화면 패턴을 갖춘 디자인 시스템이 필요할 때
- 실제로 동작하는 인터랙티브 프로토타입을 만들 때
- 시각적 구성, 접근성, 상태 전환, 작업 흐름을 리뷰할 때
- 기존 UI의 외형과 동작을 유지하며 재현하거나 다른 프레임워크로 옮길 때

리뷰만 요청하면 산출물을 수정하지 않고 발견 사항, 근거, 검증 한계를 보고합니다. 구현이나 수정이 요청된 경우에는 해당 범위의 변경과 검증까지 진행합니다.

## 사용 예시

스킬을 지원하는 에이전트 환경에서 `design-sense`를 지정하고 원하는 결과를 설명합니다. [에이전트 설정](agents/openai.yaml)에 정의된 기본 호출 예시는 다음과 같습니다.

```text
$design-sense로 이 제품의 요구사항을 해석하고 필요한 설계 문서를 파생해
실제 동작하는 인터페이스를 구현·검증해줘.
```

작업 범위를 좁혀 요청할 수도 있습니다.

```text
design-sense를 사용해 예약 화면의 날짜 선택, 입력 오류, 완료 후 흐름을 개선해줘.
기존 디자인 시스템과 기술 스택을 유지해줘.
```

```text
design-sense로 현재 대시보드를 리뷰해줘.
파일은 수정하지 말고 정보 위계, 데이터 비교, 키보드 조작 문제를 근거와 함께 정리해줘.
```

```text
design-sense로 제공한 원본 UI를 재현해줘.
컴포넌트의 외형, 상태, 포커스, 취소 동작과 모션을 유지하고
원본과 구현 결과를 같은 조건에서 비교해줘.
```

요청에 사용자 목표, 핵심 시나리오, 기존 화면이나 소스, 유지해야 할 디자인, 대상 기기와 기술 스택을 포함하면 설계와 검증의 기준을 명확히 할 수 있습니다.

## 작업 방식

1. **현재 프로젝트를 이해합니다.** 요구사항, 기존 UI와 코드, 디자인 결정, 토큰과 컴포넌트를 확인합니다. 사용자가 정한 시각적 방향과 기존 관례를 존중하고, 국소적인 수정은 해당 범위에 한정합니다.
2. **필요한 결정을 기록합니다.** 큰 제품 작업이나 재설계에서는 사용자 목표, 첫 화면에 필요한 정보, 상태 전환, 유지할 작업 상태와 미해결 질문을 기존 설계 문서 또는 `DESIGN.md` 같은 작은 문서에 기록합니다. 제약, 임시 선택, 가정을 구분합니다.
3. **디자인 시스템을 확인하거나 구축합니다.** 활용 가능한 시스템을 확장하고, 없다면 필요한 토큰과 재사용 컴포넌트, 상태와 반응형 동작을 구현해 실행 가능한 미리보기로 확인합니다. 이후 요청된 제품 화면까지 이어서 구현합니다.
4. **대표 흐름을 끝까지 구현합니다.** 첫 동작 화면과 서로 다른 상태를 실제에 가까운 콘텐츠로 렌더링해 정보 위계, 밀도, 작업 공간을 평가합니다. 불확실한 상호작용은 초기에 시험합니다.
5. **관찰에 따라 수정합니다.** 화면이나 동작이 설계 의도와 다르면 구현과 결정 기록을 함께 갱신합니다. 반복되는 역할은 공유 스타일과 컴포넌트에 연결합니다.
6. **결과와 근거를 전달합니다.** 핵심 시나리오, 시각적 관찰, 실제 입력과 상태 변화, 발견된 결함을 확인하고 영향을 받은 부분을 재검증합니다. 실행 방법, 산출물, 확인한 내용과 확인하지 못한 범위를 보고합니다.

문서는 작업에 필요한 결정에서 파생합니다. 모든 프로젝트에 동일한 문서 묶음을 만들거나, 근거 없는 페르소나·연구 결과·수치를 채우도록 요구하지 않습니다.

## 핵심 설계 원칙

- **의도:** 사용자가 현재 상태에서 무엇을 판단하거나 수행해야 하는지 정합니다.
- **위계:** 중요한 정보와 행동이 먼저 읽히도록 시각적 비중을 배분합니다.
- **그룹화:** 간격과 정렬로 콘텐츠, 객체, 행동의 소속을 표현합니다.
- **행동 단서:** 요소가 암시하는 조작을 실제 동작이 충족하도록 합니다.
- **연속성:** 화면 전환과 비동기 작업 중에도 포커스, 선택, 초안과 위치를 유지합니다.
- **일관성:** 같은 역할에는 같은 규칙을 적용하고, 차이는 사용자 작업의 필요로 설명합니다.

판단 항목은 [knowledge/index.md](knowledge/index.md)에서 찾고, 현재 결정에 관련된 문서만 추가로 읽습니다.

## 기술 스택과 재현 정책

새 디자인 시스템과 인터페이스는 사용자가 다른 스택을 지정하지 않으면 **React와 StyleX**를 사용합니다. 기존 애플리케이션에서는 마이그레이션 요청이 없는 한 현재 기술 스택을 유지합니다.

충실한 UI 재현은 일반적인 신규 설계와 별도 절차를 따릅니다. [source-reconstruction.md](references/source-reconstruction.md)에 따라 원본의 컴포넌트와 상태를 조사하고, DOM·CSS·JS 근거를 구현과 연결합니다. 같은 테마, 뷰포트, 콘텐츠와 상태에서 외형·동작·모션을 비교하며, 관찰한 사실과 코드 추적, 추론을 구분합니다. 일부 자산 교체가 허용되어도 다른 디자인 변경까지 허용된 것으로 해석하지 않습니다.

## 검증과 완료 기준

검증 범위는 변경의 크기와 영향에 맞춥니다. 핵심 흐름의 초기 상태, 실제 조작, 기대 결과와 관찰 결과를 기록하고, 관련된 취소·Undo·오류 복구·탐색 복귀·비동기 완료 등을 확인합니다. 기본 화면뿐 아니라 활성 상태와 긴 텍스트, 빈 데이터, 혼합 값 등 까다로운 상태도 살펴봅니다.

중요한 조작은 키보드와 실제 포인터 입력으로 확인하고, 드래그 조작에는 필요한 대체 경로를 점검합니다. 입력 값과 저장 데이터, 포커스와 다음 작업 위치까지 관찰하며, 화면 간 반복 역할의 스타일과 동작도 비교합니다.

소스 검사, 빌드 성공, 상태 테스트, 스크린샷은 각각 다른 근거입니다. 빌드 성공만으로 시각적 품질이나 상호작용 성공을 판단하지 않습니다. 브라우저나 기기 관찰이 불가능한 경우에는 검증하지 못한 부분을 명시합니다. 최종 산출물에는 실행 가능한 진입점 또는 실행 방법, 관련 파일, 검증 결과와 남은 한계가 포함됩니다.
