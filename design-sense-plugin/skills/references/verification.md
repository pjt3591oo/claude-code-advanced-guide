# Evidence before completion

Evaluate against the agreed user outcome and reference, not merely the implementation's current feature list. Separate model tests, browser interaction evidence, visual observation and claims not tested. Use the tools available in the session; if a tool is unavailable, report the unverified portion precisely.

For each core scenario record the initial state, actual actions, expected result and observed result. Complete a user-created case from an empty state when creation is part of the product. Vary a relevant date, owner or optional value beyond the fixtures, then find the result through normal navigation or filtering; creation and discovery must cover the same supported range. Check a representative full journey plus its risky transitions: commit/cancel/Undo, selection change, error recovery, navigation return with unfinished input, reload, or asynchronous completion as relevant. Tests should fail on a plausible behavioral regression, not on a reworded heading.

Inspect the rendered default, active and difficult states. Apply the three composition scales. Check clipping/overflow, real text, alignment, contrast, visible focus and readable labels. Exercise keyboard and a non-drag path for important drag operations. A static screenshot cannot validate history or state continuity; passing state tests cannot validate affordance or hierarchy.

Where fixed regions or changing viewport bounds can cover input, focus and type through the actual journey. Inspect the caret, entered text, relevant error and path to the next action after focus and scrolling. Successful typing or a partly visible field does not establish usable editing. Exercise software-keyboard opening and dismissal on a supported browser when available; desktop keyboard tests do not cover that behavior. Record unavailable observations explicitly.

For a workflow spanning several screens, compare recurring roles across those screens: text styles including leading/tracking, shape families, internal spacing, optional content, emphasis and state treatments. Explain meaningful differences through the task; correct arbitrary drift in the shared rule. Inspect scroll positions and transitions as well as resting screens, using [motion](motion.md) where change carries meaning. Exercise any indicator's actual state change and a date beyond the initial visible period when present. Record concrete mismatches and unresolved choices; a token inventory or successful booking is not evidence of this comparison.

Vary zero, one and several items when cardinality changes available actions. A one-item collection may not need paging controls; a multi-page collection can retain disabled previous/next controls at its boundaries. For dependent forms, inspect before and after a prerequisite is supplied: distinguish unanswered, available and unavailable options, and check that status copy follows the actual condition. Then change the prerequisite and inspect which answers remain valid, which need correction and where interrupted work resumes.

Judge visual fit against the intended first viewport and comparable reference before reading automated style findings. Name concrete mismatches in hierarchy, density, content rhythm or working space; changing a font or palette does not repair a structural mismatch. Treat detector findings as candidates to triage, and a clean scan as limited evidence, never a visual-quality verdict.

For automated acceptance, tie each applicable constraint to the current artifact and state, an actual observation and a result. Separate required contracts, recommendations and unresolved design judgment; an aggregate score must not hide a failed required contract. Missing, stale or unexecuted checks remain unverified. After a relevant change, renew the affected evidence. If repeated repairs expose a conflicting rule or unsupported capability, revisit that decision instead of cycling for a higher score or silently weakening the check.

Try the behavior the interface advertises: an actual keyboard shortcut, a purported scrub target, and an exact field edit with Enter, Tab and Escape. Observe the affected object or saved data as well as the field display. Check one asymmetric or mixed-value case where applicable. A successful happy-path click does not cover those distinct contracts.

For fields, pickers and overlays, run the applicable sequences in [component behavior](component-behavior.md), including return after commitment or cancellation. Check the recorded primitive choice against its disproof scenario and verify the native responsibilities retained by any hybrid construction. Derive expected outcomes from the agreed contract before comparing the implementation. Observe value changes and callback effects across the full event sequence: restoring displayed text is insufficient if a subsequent blur saves the canceled draft. Test within the owning form or nested overlay when those contexts change event routing. Treat visual, behavioral and motion results separately; matching outer dimensions can still hide broken internal alignment, and a passing render test covers neither.

Exercise multi-event interactions through the actual pointer and keyboard: for example, double-click to edit text, then type, commit or cancel, and select another object. Rendering must preserve the ongoing event sequence and intended focus. A working handler or an alternative inspector field does not verify the advertised direct-edit path.

When shortcuts, selection or custom pointer gestures are present, exercise the relevant conflicting sequences in [keyboard and pointer interaction](keyboard-pointer.md); a command working in isolation does not establish correct routing during another interaction.

For quantitative displays, use the applicable [chart checks](charts.md#verify-the-claim); correct-looking marks can still misrepresent their data.

When comparing with a reference product, use equivalent tasks and selection states. Distinguish reference behavior directly observed, documented by its maker, and inferred by you. For inspiration or redesign, compare task success, clarity, continuity and interaction effort before pixel similarity. For faithful reconstruction, apply [source reconstruction](source-reconstruction.md): visual geometry, state behavior and motion are acceptance requirements alongside task success. Source collection, module indexing, export counts and passing render tests do not establish reconstruction coverage or parity.

Record failures with reproduction steps and impact. Repair within the authorized scope and rerun affected checks. If fixing a defect changes the design decision, update that decision where it is owned. Keep open defects visible; do not rewrite acceptance criteria to fit a weak result.

Completion evidence should include a runnable entry point, artifact links, tested scenarios, visual observations and explicit limits. If browser testing was blocked, a build success remains build evidence only.
