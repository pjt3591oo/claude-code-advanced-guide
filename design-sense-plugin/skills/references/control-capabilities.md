# Choose the control's implementation boundary

Use this reference when selecting or replacing a control. Read rows relevant to the actual inventory; each row is a capability probe, not a required feature set or a ban on its native counterpart. For reconstruction, the source instance supplies the contract. For new work, the task and supported environments supply it.

## Translate the supplied design into implementation requirements

When a designer supplies a screen, component specification or prototype, treat its intended anatomy, dimensions, alignment, content slots, states and motion as implementation requirements. Break a designed control into its cooperating parts and state owners before selecting HTML elements. A one-to-one mapping from design-component names to tags can omit most of the component. Visual fidelity is a valid reason for composition or customization even when a native widget performs the basic operation.

For each consequential requirement, connect `design evidence → required appearance/behavior → responsible part or adapter → rendered verification`. Keep observed or specified requirements distinct from inferred behavior. Resolve consequential gaps in the design without inventing features or requesting permission for routine implementation choices. Evaluate native, hybrid and custom options against these requirements; implementation convenience does not authorize reducing the supplied design.

For example, a selection field with an icon, secondary text, a selected indicator and an anchored scrolling list needs all those parts and their states. A multiline composer with an inset action and capped growth needs coordinated text, action, sizing and scroll behavior. A numeric property field with a unit suffix and drag label needs display, draft parsing and pointer interaction to agree. These are composition requirements when present in the design, not decorations to approximate with a similarly named tag. Use the family probes below to uncover the responsibilities behind such parts.

## Assign responsibilities before selecting a primitive

Consider native controls with scoped styling, hybrid controls retaining native editing or form elements, and custom widgets with explicit interaction semantics. Choose the smallest construction that satisfies the required opened, editing and return states. A headless library supplies reusable behavior but its defaults still need comparison with the contract.

Identify which node owns visible paint and geometry, pointer/keyboard interaction, text editing, and form value/validation. These may be different nodes. Inspect computed visibility, accessibility exposure, event handlers and active render branches: a hidden input may bridge form submission while a button and list own selection. A native input can also remain the actual editor inside a custom field.

Check current platform capabilities and target-browser support when a decision depends on a claimed limitation. Customizable select rendering, native popovers, dialog behavior, intrinsic-size transitions, field sizing and scrollbar styling can change the tradeoff. Verify the required capability rather than repeating a historical limitation. A plain selector or fixed-size text field may already fulfill the task; custom construction should address an identified gap.

## Capability probes by family

| Family and native starting point | Required capability that can change the construction | Boundary and disproof probe |
| --- | --- | --- |
| Select — `select` | Rich option layout, selection summaries, preview, popup geometry or multiple-selection presentation | Inspect the actual open UI. Distinguish a visible native picker from a hidden form bridge or fallback. Cancel a tentative choice and reopen; compare active and committed values. |
| Combobox — `input` with `datalist` | Controlled filtering, remote results, virtualization, multiple values or strict existing-identity selection | Retain text editing where suitable; own the query/list interaction explicitly. Test unmatched text, empty results and late results after dismissal. Typing is not necessarily selection. |
| Number field — `input[type=number]` | Localized parsing, currency/units, expressions or custom stepping/scrubbing | A text input with an appropriate input mode may own draft text while parsed data remains numeric. Check incomplete drafts, paste, empty values, modifiers and one final commit; formatting must not destroy an in-progress edit. |
| Date/time or range picker — date/time inputs | Unavailable dates, multiple months, calendar systems, time-zone rules or range selection | Choose the required field/calendar composition. Probe the relevant boundary date, partial input, an incomplete range and cancel/reopen. Keep the stored date/time meaning distinct from display formatting. |
| Color picker — `input[type=color]` | Embedded channel controls, a two-dimensional area, palette selection or linked representations | Compose only the required channels and views; preserve any hidden inputs serving assistive interaction. Change one representation and verify the others and final stored value. Check current native capabilities before declaring a channel unsupported. |
| Slider — `input[type=range]` | Multiple thumbs, minimum separation, snapping or preview-versus-commit | Inspect which track/thumb owns movement and which input supplies form or assistive semantics. Test a boundary, crossing policy, cancellation and release outside the track; one gesture must respect the agreed commit boundary. |
| Checkbox, radio and switch — native choice inputs | Specific geometry, mixed-state paint, switch motion or custom hit areas | Native inputs with scoped appearance or visually hidden inputs may retain useful semantics. If roles replace them, account for keyboard and form responsibilities. Test label activation, keyboard focus, mixed/disabled state and reset; a duplicate input must not create a second unintended tab stop. |
| File upload — `input[type=file]` | A custom trigger, drop target, preview list or upload lifecycle | Keep file selection connected to the browser picker; separately own upload progress and failure. Test chooser cancellation, selection, removal and choosing the same file again where supported. A styled trigger alone is not an upload workflow. |
| Textarea — `textarea` | Automatic height, row limits, draft submission or editing conventions | Keep native text editing when appropriate and add the necessary measurement/event adapter. Test growth and shrinkage after typing, external updates and width changes, then scrolling at the cap. Rich-text structure is a separate editing requirement. |
| Popover — `popover` attribute | Anchor collision handling, nested surfaces, close veto or product-specific focus policy | Compare placement, dismissal, logical ownership and state integration rather than assuming platform support is absent. A child popup interaction must have the intended effect on its parent. |
| Dialog — `dialog` | Controlled lifecycle, nested overlays, draft policy or coordinated exit | Native modality/focus support may be sufficient. If custom plumbing is used, explicitly own focus containment/return, background interaction and dismissal. Test a close request during editing and an interrupted exit. |
| Tooltip — `title` | Keyboard access, controlled delay, placement, re-entry or styled content | Verify hover and keyboard-focus lifetimes, Escape and overlay ownership. A browser title tooltip does not establish these contracts. Content requiring user actions needs an appropriate interactive surface. |
| Accordion — `details`/`summary` | Heading navigation, horizontal layout, controlled expansion or coordinated motion | Native disclosure may suffice, including grouping where supported. Test the required focus/navigation model and whether collapsing preserves child state; an animated wrapper is not a complete interaction model. |
| Scroll area — native overflow | Overlay scrollbar geometry, visibility policy or synchronized scroll surfaces | Preserve native scrolling when it meets the task; custom scrollbars need not replace the scroll engine. Test wheel/touch, keyboard and focus-driven scrolling, nested boundaries and layout occupancy. |

## Verify the retained and replaced layers together

For applicable form controls, exercise submission, reset, validation, disabled/read-only state and autofill when required. Ensure hidden bridges and visible values stay synchronized, and auxiliary actions do not submit accidentally. For text editing, retain composition, selection and caret behavior. For custom widgets, account for accessible names, roles, values and keyboard operation rather than adding roles to a click-only surface.

Run the relevant [behavior sequences](component-behavior.md) in the owning form, narrow container or nested overlay. Inspect computed dimensions and winning rules in both resting and active states. Document the chosen boundary and remaining evidence gap alongside the existing component record; do not create a second catalog of unverified implementations. A replacement is complete only when the required behavior, layout and motion pass their respective checks.
